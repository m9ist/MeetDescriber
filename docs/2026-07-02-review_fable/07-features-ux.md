## Резюме

**Оценка зрелости продукта: 6.5/10** — как личный инструмент автора; **3/10** — как продукт «для коллег».

Основной сценарий («открыл Meet → запись пошла → встреча кончилась → три документа») работает
end-to-end и обвешан продуманными деталями: идемпотентный pipeline с кэшем диаризации,
перезапуск любого этапа, merge двух встреч, drift-alert, «не записывать эту встречу»
с полным удалением следов, логирование каждого UI-действия. Это уровень инструмента,
которым автор реально пользуется каждый день и точит по живым болям — это видно по git log.

Слабые места — не в happy path, а вокруг него:
1. **Восстановление после сбоев**: упавшее приложение оставляет сессию-сироту без job,
   которую нельзя обработать из UI; ошибка захвата (диск кончился, устройство отвалилось)
   молча убивает поток записи, а трей продолжает показывать «Записывает».
2. **Второй Meet-таб** ломает остановку записи первого (баг в `_handle_meet_ended`).
3. **Onboarding** — 8–10 ручных шагов, включая сборку exe PyInstaller'ом и передачу
   extension ID руками; коллега без помощи автора не взлетит.
4. Нет уведомления «документы готовы», нет настроек в UI, нет автозапуска с системой.

## 2. Пробелы в основном сценарии

### 2.1 Приложение упало посреди встречи — ⚠️ аудио цело, но обработать нельзя
Чанки пишутся на диск каждые 30 сек (`CHUNK_DURATION_SEC=30`, config.py:60) — теряется максимум
последние ~30 сек. Но: строка `sessions` остаётся без `ended_at`, а **job создаётся только в
`_stop_and_offer_processing`** (main.py:430). После рестарта `init_db()` чинит только зависшие
`processing` jobs (db.py:68), сессий-сирот без job он не касается. В «Все совещания» такая сессия
видна (LEFT JOIN, meetings_repo.py:53), аудио на месте, но «Перезапустить транскрипцию» упрётся в
`job_id is None` → «Задание не найдено в БД» (meetings_window.py:381). Итог: запись есть, но из UI
она мертва.
**Фикс дешёвый:** в `init_db()`/старте — для сессий с чанками и без job создавать pending job и
проставлять `ended_at` по mtime последнего чанка.

### 2.2 Две встречи: подряд — ок; параллельно — баг
Подряд: работает, `_skip_tab_ids` корректно чистится. Параллельно (второй Meet-таб при идущей
записи): `_handle_meet_started` молча игнорирует (main.py:270) — приемлемо, хотя пользователь не
узнаёт, что вторая встреча не пишется. Хуже: **`_handle_meet_ended` не сверяет tab_id**
(main.py:292–296) — закрытие второго (не записываемого) таба вызовет `_stop_and_offer_processing`
и остановит запись **первой** встречи посреди разговора. Для сценария «глянул ссылку на другую
встречу и закрыл» это реальная потеря записи. Фикс — одна проверка `tab_id == self._current_tab_id`.

### 2.3 Встреча 3 часа — память ок, диск заметный, claude-этап под угрозой
Память: буферы сбрасываются каждые 30 сек — ок. Диск: 48 кГц stereo 16-bit ≈ 0.66 ГБ/час чанков
+ merged.wav такого же объёма при обработке ≈ **4 ГБ на 3-часовую встречу**. Терпимо, кнопка
«Удалить аудио старше 14 дней» есть. Транскрипция GigaAM ~28x realtime — ок. Но:
`ClaudeManualDialog` гонит **всю транскрипцию инлайн в stdin** claude с `timeout=300`
(dialogs.py:326–336) — на 3-часовой встрече транскрипт в сотни КБ: либо не влезет в контекст,
либо не уложится в 5 минут → «Ошибка: rc=...», и пользователю остаётся ручной путь через
«Скопировать промпт». Таймаут стоит поднять и/или сделать зависимым от объёма.

### 2.4 Диск кончился — тихая смерть записи
`_save_wav` бросит OSError → выпадет из `_flush_chunk` → `_capture_loop` поймает и вызовет
`on_error`, который **только пишет в лог** (main.py:387: `lambda e: log.error(...)`). Поток
захвата умирает, `_recording` остаётся True — **трей и спектр продолжают показывать «Записывает»**,
пока пользователь не остановит вручную и не обнаружит обрубок. Нужен UI-алерт в `on_error`
(toast + смена статуса) — сейчас это самый обманчивый отказ в системе.

### 2.5 Забыл включить приложение, вспомнил в середине встречи
Автостарта не будет: extension шлёт `meet_started` только на `tabs.onUpdated status=complete`
(background.js:60) — уже открытый таб события не даст. Рабочий обход: трей → «Начать запись
вручную» (диалог + Enter). Приемлемо, но никто не подсказывает; F5 на Meet-табе тоже сработал бы.
Связано с отсутствием автозапуска приложения при логине (см. §3).

### 2.6 Chrome extension / хост отвалился
Устойчивость неплохая: background.js реконнектится каждые 5 сек (background.js:23), host bridge
делает 2 попытки TCP с переподключением (native_host.py:66), при занятом порте второй экземпляр
app честно логирует (main.py:199). Но **вся диагностика — только в логи**: если хост не
зарегистрирован / exe не собран / расширение выключено, приложение выглядит полностью здоровым и
просто никогда не автостартует. Ни индикатора «расширение на связи» в трее, ни B11-подсказки.
Пользователь узнаёт о проблеме постфактум — пропущенной записью.

### 2.7 Пропущенный Allow (macOS)
Лучший из пробелов: при молчащем tap и живом mic пишется warning в лог с точной инструкцией
(audio_capture.py:449–456), но **тоста нет** — не-программист app.log не откроет. Запись пройдёт
«успешно», в транскрипции будет только голос самого пользователя. Механизм тостов уже есть
(mic_drift_warning) — подключить к нему этот warning почти бесплатно и спасает целую встречу.

## 4. UX-шероховатости в существующих флоу

### ClaudeManualDialog: цена одной встречи в кликах
Happy path после встречи: тост «Обработать сейчас» (1 клик) → транскрипция/диаризация идут сами →
диалог «анализ» → «Запустить» (2) → диалог закрывается сам при успехе → диалог «follow-up» →
«Запустить» (3). **Итого 3 клика и два ожидания у диалогов**, которые появляются в непредсказуемый
момент (спустя 5–15 минут после нажатия «Обработать»). CLAUDE.md называет это «основным путём, не
fallback» — осознанное решение из-за запрета API, но: (а) диалог `-topmost` выпрыгивает поверх
работы; (б) если пользователь ушёл, `result_q.get(timeout=1800)` через 30 минут молча уронит job
в error, который к тому же исчезнет из трея (см. B13). Дешёвое улучшение в рамках ограничения
«только CLI»: чекбокс «запускать claude автоматически для обоих этапов» — тогда диалог показывается
только при ошибке, и встреча обрабатывается в 1 клик.

### Onboarding нового пользователя (Windows): ~10 ручных шагов
venv → `pip install -r requirements-windows.txt` (CUDA-стек, ~10–15 мин) → `.env` + получить
HF-токен + **вручную принять условия 3 gated-репо pyannote на HF** (нигде в README не расписано,
только «токен с доступом к gated») → установить и залогинить Claude Code → **собрать
for_meets_host.exe PyInstaller'ом** (README про это молчит — `install_host.py` просто упадёт с
FileNotFoundError, текст ошибки, к счастью, содержит команду) → загрузить распакованное расширение
в chrome://extensions → скопировать extension ID → `python -m app.extension.install_host
--update-id <ID>` → `python setup.py` для проверки → запуск. Для не-программиста — непроходимо;
для программиста — вечер. `setup.py` (H1–H8) — сильная сторона, но он диагност, а не установщик.

### Понятность ошибок для не-программиста
- «Ошибка: rc=1: ...stderr[:200]» в ClaudeManualDialog — техножаргон;
- `modal.update("error", str(e)[:60])` — обрезанный Python-exception в статус-окне;
- «Нет аудиофайлов в сессии» — хорошо;
- главная проблема — не формулировки, а то, что **значительная часть отказов вообще не имеет UI**
  (ошибки захвата, молчащий tap, мёртвый мост) и живёт только в app.log.

### Мелочи
- dialogs.py:388–389 — дублированная строка `self._set_status("Промпт скопирован...")` (копипаста).
- «Не записывать эту встречу» теперь **удаляет** уже записанное — из текста кнопки это не следует;
  пользователь, нажавший её в середине встречи «чтобы дальше не писалось», потеряет начало без
  подтверждения.
- Тост автостарта живёт 9 секунд; отойдя за кофе, отказаться от записи уже нельзя (только стоп
  через трей — а он не удаляет).
- В tray-меню error-задания не видны вовсе (см. B13) — «встреча пропала».

## 5. Готовность «поделиться с коллегами»

Что мешает прямо сейчас, по убыванию блокирующести:

1. **Нет installer'а/бандла (Win)** — на Mac есть `create_mac_app.sh` → .app; на Windows —
   голый репозиторий + venv + `start_windows.vbs`. Коллеге нужен хотя бы `setup_windows.ps1`,
   который делает venv, ставит зависимости, собирает host.exe, регистрирует реестр.
2. **for_meets_host.exe не в репо и его сборка не документирована в README** — первый же шаг
   `python app/extension/install_host.py` из README упадёт.
3. **Extension ID** меняется у каждого при загрузке распакованного расширения — шаг
